# Data, shards and read routing

If a rule here conflicts with `AGENTS.md`, stop and ask. The tests at the end are the acceptance criteria.

## Schema conventions

- Money columns are integers in minor units (see `money.md`). Timestamps are `timestamptz`, stored in UTC.
- Every team-owned table has a `team_id` column, and every query on it filters by the caller's team.
  *Why: team isolation is enforced on the server (`security.md`).*
- Settings rows carry an `updatedAt` set by the server, never by the client (brief, Requirement 7).
- **`team_id` is generated by the server before the first insert.** *Why: the shard is chosen from it, so it
  must exist before any row is written.*

## Migrations

- Prisma Migrate, through the **direct (unpooled)** URL configured in `prisma.config.ts`. *Why: Prisma's
  migration engine does not work through PgBouncer.*
- Both shards always run the same migrations: deploy to shard A, then shard B, and check both report the
  same applied list. A migration that succeeded on only one shard blocks all further work until fixed.
- Never edit or delete an applied migration; never change the schema once data exists without asking
  (`AGENTS.md`). Breaking changes use expand-then-contract across separate migrations.

## Sharding (brief: two databases, routed by a hash of `team_id`)

- Two Neon projects, shard A and shard B, each with its own primary and read replica.
- **Shard function, fully specified:**
  1. `team_id` is a UUID in canonical form: lowercase, hyphenated, 36 characters.
  2. Encode that string as UTF-8 bytes and take SHA-256.
  3. Read the first 4 digest bytes as an **unsigned big-endian** 32-bit integer.
  4. That integer mod 2: 0 → shard A, 1 → shard B.

  *Why: identical in every process and restart. It aims for an even spread; it doesn't guarantee perfect
  balance. Changing it can move teams between shards, so it never changes without an ADR and a migration
  plan.* Fixed test vectors (must match exactly):

  | `team_id` | First 4 bytes | Integer | Shard |
  |---|---|---|---|
  | `00000000-0000-4000-8000-000000000001` | `11e594f4` | 300258548 | A |
  | `00000000-0000-4000-8000-000000000002` | `e79acd97` | 3885682071 | B |
  | `3f2b8c1e-9a4d-4e7b-b1c2-5d6e7f809a1b` | `5b9edf31` | 1537138481 | B |
- All team-scoped access goes through one router: `getShard(teamId)` returns that shard's Prisma clients.
  Never import a shard's client directly.
- **No transaction spans both shards.** `$transaction` is atomic within one shard only. Work that must
  touch both is split into separate idempotent steps recorded as work rows (`jobs.md`).
- `SHARDING.md` must cover: the key, the hot-shard risk (one very large team sends most traffic to one
  shard; mitigation is moving that team to its own shard through a directory override — documented, not
  built), and which queries got harder (anything across teams: admin totals, global search, a user's
  teams if they span shards).

### Where non-team data lives (decided)

- **Shard A holds the global identity tables:** users, credentials, refresh-token records and user-level
  settings, plus the **user→team directory** (`user_teams`, ADR 0013). Record the extra load on A in
  `SHARDING.md` as a known imbalance.
- **The team's own shard holds** memberships, roles, shifts, swaps, activity, billing and the ledger.
- **Invites belong to the team:** the authoritative invitation lives on the team's shard. A global lookup
  on shard A (invite token hash → `team_id`) exists only if needed to locate it.
- **No foreign keys across databases.** A row on shard B can't reference a user on shard A with a
  database constraint. The application checks references, and cross-database writes are idempotent
  steps recorded as work rows (`jobs.md`), **except the user→team directory below**.
- **Exception: the user→team directory (`user_teams`, on shard A; ADR 0013).** It answers "which teams is
  this user in?" without asking both shards. It is a lookup hint, never proof of membership: the
  membership on the team's shard is the only authority, and every directory read is verified against it.
  It is written in a fixed order **instead of** as a work row, because a work row runs after the main write
  and a team the user has just created must be listable at once:
  - **Joining (create team, accept an invite): the directory row first, then the membership.**
  - **Leaving (leave, removed): the membership first, then the directory row.**
  - The insert is idempotent (`ON CONFLICT DO NOTHING`).

  *Why: whichever step a crash interrupts, what is left is a directory row with no membership, which is
  inert (reads verify, access never consults the directory). The directory may over-report but never
  under-report. Every membership writer must follow these orders; a membership written without its
  directory row is invisible to its user. Orphan rows are swept by a follow-up job.* Any other
  cross-database write stays a work row.

## Prisma clients and pools

- Prisma 7 with `@prisma/adapter-pg`. Each shard has a primary client, extended with
  `@prisma/extension-read-replicas` over a replica client.
- Documented routing: reads go to the replica; writes and `$transaction` go to the primary;
  `$primary()` forces the primary. **Raw queries go through the routing function, which names
  `$primary()` or `$replica()` explicitly** — the docs don't say where raw queries go by default.
- Runtime uses the pooled `-pooler` URLs. Confirm the replica's pooled connection string in Neon before
  relying on it; the docs checked didn't show it.
- **Not available through Neon's transaction-mode pooler:** `SET`/`RESET`, `LISTEN`/`NOTIFY`,
  session-level advisory locks, SQL-level `PREPARE`. Never design anything that needs them.

Pool maximums (not continuously open connections):

| Process | Per shard primary | Per shard replica | Total |
|---|---|---|---|
| API | 5 | 5 | 20 |
| Worker | 3 | none | 6 |

**Up to 26 client connections across one API instance and one worker instance**; more instances multiply
it. The worker uses primary clients only (billing, reconciliation and job state all need the primary).
These are a starting proposal: the k6 report measures API latency, database time and pool wait
separately, and the numbers change if they show a bottleneck. Neon's large pooler allowance does not prove
the database isn't the bottleneck.

## Read-your-own-writes (5 seconds)

The brief requires reads right after a user's write to come from the primary. We use 5 seconds.

**This design is valid for exactly one API process.**

- After every committed write, the request handler records the user ID and commit time in an
  **in-process map**, before sending the response.
- A read by a user with an entry younger than 5 seconds goes to the primary.
- **Startup fallback:** for the first 5 seconds after the process starts, every read goes to the primary.
  This covers a crash between commit and response, which loses the map.
- **Some reads always go to the primary**, whatever the marker says, because they depend on writes made
  by someone else or by another process:
  - billing and subscription state;
  - refresh-token reuse checks and revoked sessions (including "log out of all devices");
  - password-reset tokens and invitation consumption;
  - permission checks: memberships and roles. A user's own marker can't see a manager changing their role.
- **Token consumption and rotation are atomic:** one conditional update (e.g. `WHERE used_at IS NULL`,
  returning the row) or a locked row inside a transaction. Read-then-write in two steps is never allowed.
- **Expired entries are removed:** deleted when read, and by an in-process sweep every few seconds (no
  I/O). The map only holds users who wrote in the last 5 seconds.
- **One routing function decides every read**, for Prisma model queries and raw queries alike. Nothing
  outside it calls `$primary()` or `$replica()`. *Why: a raw query that picks its own client bypasses
  the 5-second rule.*
- Every read logs `db_route` and its reason: `marker`, `startup`, `primary-required` or `none`.
- No Valkey marker. *Why: it added failure modes (lost on restart, deletion without disconnect) and gives
  a single process nothing.* This map is not a rate limiter, so the in-memory rule doesn't apply.

**Enforcing one API process:**

- The host runs **1 API instance with a stop-then-start deploy**, so the old process stops before the new
  one starts and the startup fallback covers the old process's last writes. **Whether the chosen host
  supports this is unverified; until it is, this design is conditional.** A rolling deploy (old and new
  overlapping) breaks it.
- **A second API instance is not allowed** until this is replaced by a position-based design (comparing
  the replica's replay position with the user's last write, stored in Postgres). Record that in
  `ARCHITECTURE.md` and an ADR as "what changes in production".
- No code-level lease. *Why: a Postgres heartbeat every few seconds would keep Neon awake around the
  clock (≈ 182 CU-hours a month at 0.25 CU), about twice the free allowance.*

## Neon budget and cold starts

- Free plan: 100 CU-hours per project, shared by the primary and its replicas. **Automatic suspension
  after 5 minutes of inactivity cannot be disabled on Free**; the first query after it pays a cold start.
  Activity keeps a compute awake and spends the allowance.
- **Cap autoscaling at 0.25 CU**, raising it only for the k6 run, then lowering it again.
- Health checks never touch Postgres. Anything on a timer touching Postgres needs its CU-hour cost written
  down (see the sweep in `jobs.md`).

## Seeding

- At least **10,000** activity records (brief, Requirement 1). **Our testing choice:** one test team with
  at least 10,000 records on its own (so one feed is proven at volume), plus another team on the other
  shard (so routing is proven). All seeded through the router.
- `EXPLAIN ANALYZE` runs through `$primary()` (see the `cursor-pagination` skill).

## Tests (acceptance criteria)

Routing tests check **which client actually ran the query** (instrumented clients in tests, plus
`SELECT pg_is_in_recovery()` on that client: true on a replica, false on a primary). The log is checked
too, but never alone.

1. **Shard routing:** the test vectors above match exactly; teams seeded on both shards are found through
   the router.
2. **No cross-shard transaction:** a step that must touch both shards is a work row, not a `$transaction`.
3. **Migration parity:** both shards report the same applied migrations.
4. **Write then read at 1 second → primary.**
5. **Restart, then read immediately → primary** (`startup`).
6. **Write then read at 6 seconds → replica** (`none`).
7. **Primary-required reads → primary**, at any time: subscription status, a refresh-token check, a
   permission check made after someone else changed the role.
8. **Raw and model reads agree:** a raw read and a Prisma model read made in the same state hit the same
   client.
9. **Atomic consumption:** two concurrent uses of one refresh token or reset token → exactly one succeeds.
10. **Map cleanup:** after many users write once, the map is empty again within seconds.
11. **Pool limits:** under the k6 run, active connections never exceed the configured maximums; the report
   shows pool wait time separately.
