# Observability [self-study]

If a rule here conflicts with `AGENTS.md`, stop and ask. The tests at the end are the acceptance criteria.

**The standard (brief):** from the logs alone, answer "what happened to this user's payment at 3:14pm?"

## Request logs

- Structured JSON, one line per request, timestamps in UTC ISO 8601. The logger library is chosen in the
  ADR for the Sentry and request-ID logging slice (build order step 3). Until then the scaffold uses plain
  `console.log`.
- **Fields (brief):** request ID, user ID (when authenticated), route, response time, result. Ours: the
  route template (e.g. `/teams/:teamId/shifts`) and `team_id` rather than a raw URL, the status code,
  an error code on failure, and for reads the `db_route` and reason (`data.md`).
- **Request ID:** generated by the server per request. An incoming `X-Request-Id` is accepted only if it
  matches the expected format; otherwise a new one is generated. It is returned in the response header.
- Never log what `security.md` lists (passwords, hashes, tokens, `Authorization`, cookies, secrets, email
  bodies with links). One redaction list serves the logger and Sentry.

## Job logs (brief: every attempt)

- Every execution logs: job ID, row ID, generation, `execution_attempts`, outcome, duration (`jobs.md`).
- **Correlation IDs live in the Postgres work row** (`origin_request_id`, and `payment_operation_id`
  where relevant), not only in BullMQ job data. Jobs read and log them from the row, so a job restored by
  a recovery sweep still carries them (`jobs.md`).

## Tracing a payment

Every step logs team ID, user ID where known, its own request ID, the payment operation ID, and Stripe
IDs (Checkout session, PaymentIntent, event ID) as soon as each exists.

- **The webhook is a separate request with its own request ID.** It is linked to the original request
  through the **payment operation ID**, never by reusing the original request ID.
- **Before signature verification, log only** the webhook's request ID and the outcome (received,
  rejected). Never parse or log fields from an unverified body. Event ID and type are logged only after
  verification succeeds.

| Step | Event logged |
|---|---|
| Change requested | `payment_operation_created` (quote, base version) |
| Checkout created | `stripe_session_created` |
| Webhook arrives | `webhook_received` (request ID only), then `webhook_rejected`, or `webhook_verified` (event ID, type) |
| Job runs | `payment_confirm_attempt` with outcome: `applied`, `already_applied`, `rejected` (reason), `review` |
| Ledger written | `ledger_entries_written` (entry types, amounts) |

`docs/` keeps a short runbook: filter by user or team and time → request ID → operation ID → Stripe IDs
→ webhook request and event (joined by operation ID) → job attempts → ledger rows. Rehearse it once with a real test-mode payment.

## Sentry (brief: app and server)

- **Server:** errors tagged with request ID, user ID and team ID. User ID, never email. Scrubbed by the
  shared redaction list.
- **App:** the Expo/React Native SDK, tagging the request ID from failing responses. **It contains native
  code, so install it before the first EAS development build.**
- Source-map upload needs an auth token: build-time secret only, never `EXPO_PUBLIC_`.
- **Verify before relying on them:** Sentry's free-plan event allowance (sample if needed), and how long
  the chosen host keeps logs. If logs disappear before the demo or review, the 3:14pm question can't be
  answered; record the retention in `ARCHITECTURE.md`.

## Tests (acceptance criteria)

1. A request's log line has every field above and no redacted value.
2. A malformed incoming `X-Request-Id` is replaced; the response header matches the logged ID.
3. A job started by a request logs that request's ID, read from the work row.
4. **Recovered-job correlation:** delete the queued job, let the sweep restore it → the restored job
   still logs the original request ID and operation ID.
5. **Unverified webhook:** a request with a bad signature produces log lines with no event ID, type or
   body fields.
6. A thrown error reaches Sentry (test project) with request, user and team tags and no secrets.
7. The payment runbook, followed against one test-mode payment, reconstructs every step from logs alone.

## Decided when it was built (ADR 0039)

The rules above are unchanged. What the implementation settled:

- **One list, two copies:** `shared/sentry-scrub.ts` is canonical; `server/src/observability/sentryScrub.ts` and `app/src/observability/sentryScrub.ts` are byte-for-byte copies (`node shared/sync-sentry-scrub.mjs`), each with a parity test. Change the shared file, then sync.
- **Errors only.** Tags go on at capture time from the failing request's own data, never onto a shared scope. User: the ID only. `request` is removed from every event.
- **The gate** (CHOSEN, NOT MEASURED, Dave 2026-11-04): one event per error per 5 minutes, 10 a minute, 50 a day per server process, 20 per app session.
- **Geography:** every event carries `user.ip_address = 0.0.0.0` (the shared scrubber sets it). Sentry infers a city and country from the connection IP even with "Prevent Storing of IP Addresses" on; only the placeholder stopped it on real events. A URL inside text loses its query string, not only a URL field. Contexts are trimmed (no culture; the device keeps model, memory and kind; no per-install hash).
- **k6:** `X-Load-Test: k6` is honoured only while `LOAD_TEST_MODE=true`. With the switch off the header is ignored.
- **Retention:** Sentry's Developer plan keeps a 30-day lookback (sentry.io/pricing, read 2026-11-04). Whether its 5,000-error quota is monthly is unconfirmed. The host's own log retention is recorded in the deploy slice.
- **Test 6** (a thrown error reaches Sentry with request, user and team tags and no secrets) is covered by `sentry.unit.test.ts` and `errorReporting.unit.test.ts` for what is sent, and by the two real test events for what Sentry shows.
