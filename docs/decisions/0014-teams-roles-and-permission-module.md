# 0014: Teams, roles and the one permission module

- **Status:** accepted (2026-10-23; Dave approved the plan)
- **Date:** 2026-10-23
- **Decided by:** Dave
- **Related:** `.agents/rules/security.md` (permission table, team isolation, 404 vs 403), `.agents/rules/data.md`, ADR 0013, `docs/SECURITY.md`

## Problem

Every later team route (shifts, swaps, invites, billing) needs the same answer to "who is this person in this team, and may they do this?".
It has to be one piece of code, not a check copied into each route, and it must decide 404 versus 403 the same way everywhere.

## Options considered

1. **Check the role inside each handler.** Simple at first; one forgotten check is a security hole.
2. **Put the role in the access token.** No database read per request. But a demotion would not take effect until the token expires, which
   `security.md` forbids.
3. **One table plus one middleware** (chosen): `can(role, action)` in one module, and `requireTeamRole(action)` that loads the membership from the
   team's shard primary on every request.

## Decision

- **One permission table** in `server/src/teams/permissions.ts`, mirrored in `docs/SECURITY.md`, unit-tested against a hand-written copy of
  `security.md`. Anything not in the table is refused. Rows for later slices (`shifts.edit`, `invite.*`, `billing.manage`) already exist, so a later
  slice adds a route, not a rule.
- **`requireTeamRole(action)`** runs after the token and session check. The team comes from the validated route parameter. It reads the membership
  (with the team) from `getShard(teamId).primary`, one query, and answers: **no membership → 404** (identical to a team that does not exist);
  **membership but the role may not → 403 `forbidden`**.
- **Exactly one Owner per team**, enforced by the database: a partial unique index on `memberships (team_id) WHERE role = 'owner'`. Nobody is
  invited as Owner (`security.md`), so a second Owner is always a bug. The index is hand-written in the migration because Prisma cannot express it.
- A team's `time_zone` is stored (Figma's create-team screen asks for it) and must be in the server runtime's IANA list. `team_id` is generated by
  the server before the first insert.
- The member list returns names and roles, never email addresses.

## Why

Roles are read from the database on every request (`data.md`: permission checks are primary-required reads), so a demotion or removal applies to the
next request, tested with the same access token before and after. 404 for a stranger and 403 only for a member with too little power means a
response never confirms that another team's resource exists.

## Consequences

- One extra primary read per team request (the cost `security.md` accepts), measured in the k6 report.
- The 403 proof in this slice uses a route registered **only inside the test harness**. The brief's "Staff calls delete-shift and is rejected" test
  belongs to the shifts slice, which adds the real endpoint on this middleware.
- `create team` has no idempotency key: a network retry could create a second team, so the app disables the button while the request is out. A
  per-user limit (5 per hour) bounds the damage.
- Revisit when: a user can hold more than one role per team, or role changes need an audit trail.

## Evidence

`permissions.unit.test.ts`, `team-security.integration.test.ts` (isolation across shards, Staff 403, demotion with the same token), on the test shards.
